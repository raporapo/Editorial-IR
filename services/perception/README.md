# services/perception

The Python side of the boundary: speech recognition, vision, on-screen text and
the multimodal look at an event.

TypeScript owns the contract. This implements it, and nothing here invents a
field — the shapes come from `schemas/`, which is generated from the TypeScript
definitions and committed.

## Why the split is here and not somewhere else

Machine learning lives in Python and structured data lives comfortably in
TypeScript, so the line is drawn where that stops being a preference and starts
being a cost. Everything above this — the representation, the judgement, the
planning, the adapters — is orchestration over structured data, and is
TypeScript. Everything that wants CUDA is here.

The transport between them is JSON Lines over a subprocess. That is a detail,
not an architecture: replacing it with HTTP or a queue changes one file on each
side, because both sides only ever agreed on the schemas.

## Running it

```bash
pip install -e '.[all]'          # or a subset; see below
python -m editorial_perception   # reads requests on stdin, replies on stdout
```

Normally you do not run it by hand. `oea analyze --perception python` starts it,
talks to it and shuts it down.

## Install only what you need

Every capability is optional and the worker says which it has:

```bash
pip install -e .            # probe and prepare (needs ffmpeg on PATH)
pip install -e '.[asr]'     # + transcription
pip install -e '.[visual]'  # + frame embeddings and zero-shot labels
pip install -e '.[ocr]'     # + on-screen text
pip install -e '.[text]'    # + a real text embedding model
```

A capability whose package is missing returns `missing_dependency`, which the
compiler reads as "this stage is unavailable" and works around. That is a
different thing from a failure, and the distinction is deliberate: an analysis
with no transcript is worse than one with a transcript, and far better than no
analysis at all.

## One model at a time

Sixteen gigabytes of VRAM is the declared target, and a transcriber, a vision
encoder and a vision-language model will not fit in it together. The pipeline is
staged so they never need to: everything is transcribed, then everything is
embedded, then the events that earned it are described. `ModelScheduler`
enforces that, and caches loaders so thirty files cost one model load rather
than thirty — which is where nearly all of the wall-clock time goes.

`OEA_MODEL_SLOTS=2` raises the limit on a card that can take it.

## Configuration

| Variable | What it does |
|---|---|
| `OEA_ASR_MODEL` | Whisper size; default `small` |
| `OEA_ASR_COMPUTE` | Compute type; default `int8` |
| `OEA_VISUAL_MODEL` | Vision encoder; default `google/siglip-base-patch16-224` |
| `OEA_TEXT_MODEL` | Sentence embedding model; unset uses the hashing fallback |
| `OEA_VLM_BASE_URL`, `OEA_VLM_MODEL`, `OEA_VLM_API_KEY` | The closer look at an event |
| `OEA_MODEL_SLOTS` | How many large models may be resident; default 1 |

## The hashing embedding is duplicated on purpose

`backends/hashing.py` mirrors the TypeScript implementation exactly, and
`tests/test_hashing.py` checks it against vectors generated by TypeScript. An
index built by one side and queried by the other has to land in the same space:
if it does not, search does not fail, it silently returns noise, which is far
harder to notice than a crash.

Regenerate the golden file with `pnpm tsx scripts/make-hashing-golden.ts`.

## Tests

```bash
PYTHONPATH=src python -m pytest tests -q
```

They need no models and no media. What they check is the part that has to be
right whatever is installed: the protocol survives a handler that raises, a line
that is not JSON and a request with no id; ffprobe output maps onto the contract;
and the two runtimes agree on every vector.
